# AI Rules for Flutter – Custom Project Architecture

You are a senior Flutter engineer working on a
production-grade Flutter application with the
following structure:

├── config/
├── core/
├── features/

The project follows a feature-first Clean Architecture
with Retrofit, Dio, Injectable, APIResult, and Cubit
in some modules.

The goal is scalability, maintainability, and strict
layer separation.

-------------------------------------------------------

## 1️⃣ PROJECT STRUCTURE (MANDATORY)

### Top-Level Folders

config/
- routing/
- theme/

core/
- di/
- errors/
- extensions/
- general_cubits/
- helpers/
- localization/ 
- network/
- services/
- utils/

features/
- Organized by feature
- Each feature contains:
    data/
    domain/
    presentation/

Never violate this structure.

-------------------------------------------------------

## 2️⃣ ARCHITECTURE RULES

### DATA LAYER

Located inside:
features/feature_name/data/

Contains:
- data_source (remote/local)
- models (request/response)
- mapper
- repo (repository implementation)

Rules:
- Use Retrofit for API contracts
- Use Dio underneath
- Convert DTO → Entity using mapper
- Never expose response model to UI
- Catch exceptions and return APIResult

Repository must return:
Future<ApiResult<T>>

No raw DioException outside data layer.

-------------------------------------------------------

### DOMAIN LAYER

Located inside:
features/feature_name/domain/

Contains:
- entities
- repo (abstract repository)
- usecase

Rules:
- Pure Dart
- No Flutter imports
- No Dio imports
- No Retrofit imports
- Business logic inside usecases only

UseCase:
- Single responsibility
- Small and testable

-------------------------------------------------------

### PRESENTATION LAYER

Located inside:
features/feature_name/presentation/

Contains:
- pages
- widgets
- view_model OR cubit OR manager

Rules:
- No API calls directly
- Depends on UseCase or Repository abstraction
- UI must be dumb
- Business logic inside ViewModel/Cubit
- Proper loading, error, success states required




-------------------------------------------------------

## 3️⃣ DEPENDENCY INJECTION

Location:
core/di/

Use:
- Injectable
- get_it

Rules:
- Use @injectable
- Use @module for Dio and ApiService
- Constructor injection only
- No manual singleton creation
- No GetIt calls inside widgets

Always mention:
dart run build_runner build --delete-conflicting-outputs

when code generation is involved.

-------------------------------------------------------

## 4️⃣ NETWORKING

Located inside:
core/network/

Includes:
- dio_factory
- api_service
- api_result
- error handler

Rules:
- Centralized error handling
- Convert DioException to custom error model
- Handle:
    - Timeout
    - No internet
    - 401
    - 500
- Never log tokens
- Never expose raw exception

-------------------------------------------------------

## 5️⃣ STATE MANAGEMENT

Used patterns:
- Cubit (in some modules)
- ViewModel (ChangeNotifier style)
- Manager pattern

Rules:
- One state controller per feature responsibility
- No heavy logic inside UI
- Use immutable states (if Cubit)
- Always include:
    - loading
    - success
    - error

-------------------------------------------------------

## 6️⃣ CODE STYLE

- Line length ≤ 80 characters
- Functions ≤ 20 lines
- PascalCase for classes
- camelCase for variables
- snake_case for files
- Avoid abbreviations
- Avoid null assertion (!)
- Use const constructors
- Use developer.log instead of print

-------------------------------------------------------

## 7️⃣ MAPPING RULES

All mapping must be done in:

data/mapper/

Never map inside:
- UI
- UseCase
- Widget

DTO → Entity conversion is mandatory.

-------------------------------------------------------

## 8️⃣ ERROR HANDLING

- Use centralized ErrorHandler
- Use APIResult.failure
- No silent failure
- UI must react to failure state

-------------------------------------------------------

## 9️⃣ THEMING

Located inside:
config/theme/

Rules:
- Centralized ThemeData
- Support Light & Dark
- Use ColorScheme.fromSeed
- No hardcoded colors in widgets

-------------------------------------------------------

## 🔟 ROUTING

Located inside:
config/routing/

Rules:
- Centralized navigation
- No inline navigation logic
- Authentication guard handled centrally

-------------------------------------------------------

## 1️⃣1️⃣ WHAT NOT TO DO

❌ No Dio in Presentation
❌ No mapping in UI
❌ No business logic in Widget
❌ No direct model exposure to UI
❌ No manual dependency wiring
❌ No print debugging

1️⃣3️⃣ LOCALIZATION (TEXTS)
Decision Rule
Use this decision tree for every piece of text:

Is this text shown to the user?
→ Use easy_localization (LocaleKeys)
Is this a non-displayed constant (regex, key,
tag, log message)?
→ Use AppConstant

NEVER hardcode a user-visible string in a widget.

Setup
Translation files:
assets/translations/en.json
assets/translations/ar.json

Code generation commands (run after editing JSON):

flutter pub run easy_localization:generate -S assets/translations -O lib/core/localization

flutter pub run easy_localization:generate -S assets/translations -O lib/core/localization -f keys -o locale_keys.g.dart

Generated file:
lib/core/localization/locale_keys.g.dart


1️⃣4️⃣ ASSETS (FLUTTER_GEN – STRICT RULE)
Decision Rule

Is this asset displayed in UI (image, svg, lottie, font)?
→ Use FlutterGen (Assets.gen)

Is this a non-UI internal file?
→ Use AppConstants

🚫 NEVER hardcode asset paths inside widgets.

REQUIRED USAGE
Image.asset(Assets.images.logo.path);

Assets.icons.home.svg();

Assets.lottie.loading.lottie();
FORBIDDEN
Image.asset('assets/images/logo.png');

AssetImage('assets/icons/home.svg');

'assets/anything.png';

Any occurrence of 'assets/... must be refactored
to Assets....

SETUP (MANDATORY)

pubspec.yaml:

dev_dependencies:
  flutter_gen_runner: any
  build_runner: any

flutter_gen:
  output: lib/core/gen/
  integrations:
    flutter_svg: true
    lottie: true
ASSET DECLARATION
flutter:
  assets:
    - assets/images/
    - assets/icons/
    - assets/lottie/
CODE GENERATION (REQUIRED AFTER ASSET CHANGES)

Always run:

dart run build_runner build --delete-conflicting-outputs
GENERATED FILE LOCATION
lib/core/gen/assets.gen.dart

Import using:

import 'package:your_app/core/gen/assets.gen.dart';
ARCHITECTURE ENFORCEMENT

When generating code:

Always use FlutterGen for UI assets

Never use raw asset strings

Mention exact layer & folder location

Keep feature-based structure

Suggest asset naming improvements if needed

Trigger build_runner when asset changes occur


1️⃣5️⃣ RESPONSIVE DESIGN (STRICT RULE)
Goal

UI must adapt correctly to:

Small phones

Large phones

Tablets

Web

No fixed-width layouts allowed.

Layout Rules

✔ Use LayoutBuilder for layout decisions
✔ Use MediaQuery only when necessary
✔ Use Expanded / Flexible properly
✔ Use SingleChildScrollView for overflow
✔ Use ListView.builder for long lists

🚫 No hardcoded width/height like:

Container(width: 300)
Spacing Rules

✔ Use responsive spacing helpers (if exists in core/helpers)
✔ Otherwise base spacing on screen width:

final width = MediaQuery.of(context).size.width;
final isTablet = width >= 600;
Breakpoints

Standard breakpoints:

< 600 → Mobile

600 – 1024 → Tablet

1024 → Desktop/Web

Use:

LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth >= 1024) {
      return DesktopLayout();
    } else if (constraints.maxWidth >= 600) {
      return TabletLayout();
    } else {
      return MobileLayout();
    }
  },
);
Text Scaling

✔ UI must remain stable when text scale factor increases
✔ Test with:

MediaQuery.textScaleFactorOf(context)

🚫 No fixed-height containers for text-heavy widgets

Images & Icons

✔ Use BoxFit.cover or contain
✔ Avoid fixed image sizes
✔ Use FlutterGen for assets

Architecture Enforcement

When generating UI code:

Mention presentation layer & folder location

Separate Mobile/Tablet layouts if needed

Avoid inline layout logic inside large widgets

Keep UI dumb

Suggest layout improvements if applicable

What NOT To Do

❌ No magic numbers
❌ No pixel-perfect hard sizes
❌ No overflow-prone Rows
❌ No UI assumptions about device size

Expected Outcome

✔ Adaptive layouts
✔ No overflow errors
✔ Tablet-ready UI
✔ Web-ready UI
✔ Clean scalable presentation layer
